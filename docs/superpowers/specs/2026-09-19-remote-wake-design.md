# 手机与电脑远程开启 Windows：设计

日期：2026-09-19。设计确认：用户于 2026-09-20 回复“确认”。状态：用户选择在当前会话直接实现。仓库实现与自动验证已进行，服务端部署、Windows 实机及隔夜开机验证尚未完成；以 docs/remote-wake.md 与验证记录为准。

## 目标与已知条件

用户希望外出时使用手机或电脑开启家里的 Windows 电脑。家中有安卓手机及小米 AX3000 路由器。用户已确认 Windows 通过网线连接路由器，家中 Wi-Fi 可长期保持供电；安卓手机的具体型号与持续供电情况尚未确认。

用户补充：目前 UU 远程当天测试能够开机，但放置一天后可能失败。此为用户观察，尚未检查其实际唤醒链路或失败日志，不能归因于 UU、AX3000、安卓省电或网卡中的某一个。验收目标必须包括隔夜可用及故障可定位，不能以一次现场唤醒成功结项。

推荐链路：控制端 RDesk → HTTPS 服务端 → 家中安卓开机助手 → 局域网 WOL 魔术包 → Windows 网卡与主板。

安卓手机是明确绑定的辅助设备。此方案只使用路由器的普通局域网转发能力，不依赖 AX3000 的管理接口、第三方固件、公网 IP 或端口映射。尚未验证这台路由器的具体固件及局域网隔离配置。

首版以用户当前的 Windows 有线网卡为验证路径；Wi-Fi 唤醒须由电脑硬件、固件和驱动明确支持，不能按普通有线 WOL 保证。电脑应保持供电，网卡与固件应支持相应电源状态下的唤醒。Windows 快速启动、休眠和完整关机分别测试。

## 方案比较与选择

1. **安卓手机代发，推荐**：利用用户已有设备，控制端可以在任意网络；需要安卓助手持续在线并通过锁屏后台测试。
2. 路由器代发：不依赖手机，但需要核实并适配 AX3000 的具体固件和可用接口，首版不采用。
3. 局域网直接发送：适合在家使用，单独实现不能满足外出开机需求，首版统一走安卓助手。

## 当前代码约束

- `crates/rdesk_server/src/main.rs` 的账号设备接口仅返回新鲜 presence/preview，离线记录不能承担开机配置存储。
- `flutter_client/lib/src/screens/device_detail_screen.dart` 当前固定展示在线标识，不能把开机目标直接当作在线远控设备。
- Android 现有 `ScreenCaptureService` 属于 `mediaProjection` 服务；开机助手必须具有独立生命周期。
- `AuthProvider.logout`、账号删除和会话失效需要与开机助手停止、凭据清理同步。
- Windows 屏幕采集仍未实现；本次功能范围是开启电脑，不把电脑上线展示成 Windows 远控已可用。
- 当前工作区有 macOS 按需采集、会话和审核资料等未提交修改；实现只增量接入，不覆盖、归并提交其他修改。

## 用户流程

### 家中安卓手机

1. 登录 RDesk，在设备页进入“远程开机”，开启“将本机作为开机助手”。
2. 展示常驻通知、Wi-Fi 状态、最近连通时间及停止操作；首次启用由前台用户操作触发服务。
3. 引导检查后台运行、电池限制和供电条件。无需开启屏幕共享或授予无障碍权限。
4. 用户明确选择本助手服务的 Windows 目标；停止、退出账号、注销账号后立即停止领取及发送任务。
5. 不默认承诺手机重启或用户强行停止应用后能自行恢复；首版提示重新打开并启用助手。

### Windows 电脑

1. 在设置中开启“允许远程开机”，读取并展示物理网卡，优先推荐当前连网的有线适配器。
2. 用户确认网卡 MAC 地址，并选择同一账号下的安卓助手；目标电脑名称、选定网卡和助手绑定持久保存。
3. 提供 BIOS/UEFI、网卡唤醒能力的检查说明。读取配置不能等同于硬件实测支持；不自动修改 BIOS、电源计划或系统权限。
4. Windows 应用运行时发送目标专用的上线心跳，用于开机请求后的状态确认。
5. 系统启动到登录界面、RDesk 尚未运行时可能已经开机，但不能通过应用心跳确认。首版明确提示此限制，不静默安装系统服务或管理员计划任务。

### 外出的手机或电脑

1. 同一账号在“远程开机”中看到持久保存的目标，即便目标已离线。
2. 目标卡片显示电脑状态、助手状态和“开机”按钮。
3. 点击后依次显示“请求已提交”“信号已发送”“等待电脑上线”。收到本次请求之后的新鲜 Windows 心跳才显示“已上线”。
4. 两分钟内未收到上线证明，显示“未确认上线”，说明可能需要检查硬件设置，或电脑已启动但 RDesk 尚未运行。
5. 重复点击在同一有效请求内合并，不积压多次开机操作。

## 客户端与服务端边界

新增独立开机模块，不复用远控画面、输入指令或屏幕需求租约。Flutter 的模型、状态管理和页面与现有设备列表通过入口关联。

服务端持久保存目标及助手绑定，临时开机任务单独管理。每个对象以服务端认证的账号归属为准，不信任客户端传来的 `user_id`。每次读取、修改、发起、领取和回执均检查所属账号及设备绑定。

拟定接口族为 `/api/wake/targets`、`/api/wake/agents`、`/api/wake/requests`。覆盖目标配置、助手注册和状态、目标心跳、创建请求、助手领取、结果回执及控制端查询。使用独立受限设备凭据：助手不能读取账户密码，也不能执行任意远控命令；目标心跳凭据只能更新本目标状态。

目标包含随机标识、账号归属、名称、Windows 设备关联、选定 MAC、助手绑定及配置版本。助手凭据服务端仅保存摘要，本机使用 Android Keystore 保护的存储。所有凭据不进入 URL、通知、日志或文档。

只允许发送固定格式的 WOL 包（6 字节 `FF` 加 16 次目标 MAC，UDP 9）。MAC 必须是有效单播地址，拒绝全零、广播及格式错误地址。服务端不下发任意载荷、命令、域名或公网 UDP 目的地址；安卓根据明确选择的 Wi-Fi IPv4 接口及前缀计算局域网广播地址。

网络变化时重新核对已确认的局域网配置；无法确认目标仍在该网络时暂停发送并提示重新设置。不能只因另一网络具有相同私网地址段就认为是原网络。首版对网络替换采取保守暂停并要求用户在助手端重新确认，不依赖模糊的自动网络识别。

目标配置采用原子落盘和串行写保护；持久化失败不能报告保存成功。账号删除应同时删除开机配置及凭据，删除失败保持可恢复的一致状态。

## 后台执行与任务状态

Android 使用独立 Kotlin 前台服务，按实际网络设备交互用途声明 `connectedDevice` 类型及必要权限，通过 MethodChannel 与 Flutter 交互。领取与发送循环在原生服务运行，不依赖界面 Dart 定时器。

领取采用单个在途 HTTPS 长轮询：服务端最多等待 5 秒，客户端读取超时 12 秒；空响应和网络错误有退避，网络切换取消旧循环。连接维持不依赖屏幕常亮。前台服务本身不能保证所有厂商系统下锁屏联网，需结合电池配置和实机测试。

助手在线租约为 30 秒；租约过期展示“助手离线”，不把请求长期排队等待手机数小时后意外执行。创建请求时必须有在线助手，请求允许领取的有效期为 30 秒，等待 Windows 上线的观察窗口为 120 秒。

任务包含不可预测的请求 ID、目标/助手 ID、配置版本、签发及过期时间。每次重连、领取及真正发包前都校验过期、撤销及当前配置；旧凭据、旧配置和过期任务拒绝执行。

安卓持久记录近期已执行的请求 ID，允许回执重传但避免无界重复发送。网络异常不能保证严格恰好一次；每个有效请求至多执行一个有界发送批次，3 个相同 WOL 包、间隔 200 毫秒，并报告局部发送错误。

停用助手时先同步取消网络、排队和发包工作，再进行服务端清理；迟到网络响应不得恢复停用状态。移除绑定、注销及凭据吊销要覆盖在途任务。

## 隔夜失效的诊断与稳定性要求

开机详情展示最近助手心跳时间、本次请求领取时间、发送回执时间、Windows 上线时间及明确错误码；助手心跳只能证明助手与服务端连通，UDP 发送成功只能证明本机完成发送操作，均不能证明目标网卡收到数据。

保留有界的诊断记录：每个账号最近 50 次请求，最多保留 7 天，按到期和数量共同清理；账号删除时一并删除。记录状态和时间，不保存原始网络报文、Wi-Fi 密码或认证令牌。服务端重启后在途请求终止并显示服务中断，不重放历史请求。公开隐私说明随功能发布同步增加开机配置和有限诊断记录的用途、保留期与删除方式。

区分以下故障路径：

- 助手心跳中断：检查应用被停止、手机断电、后台联网限制及网络变化；不把它展示为 Windows 不支持开机。
- 助手在线但未领取/未回执：检查领取连接、任务权限及发送错误。
- 已发送但 Windows 未上线：检查本次实际电源状态、网卡供电和 WOL 设置，以及电脑已经启动但 RDesk 未运行的情况。

WOL 使用当前可信局域网接口的广播发送，不依赖 Windows 关机前的 IP 或路由器长期保留目标 ARP 项。该选择用于减少地址缓存相关依赖，不据此断言 UU 的隔天失败由 ARP 过期导致。

后台连接使用有限退避与重新建连，保持租约更新；无法维持时诚实显示离线。不得通过反复启动屏幕录制、持续点亮屏幕或无限重试伪装成稳定。安卓厂商省电策略和真实休眠行为需实机覆盖。

## 实现涉及的主要位置

- Rust：新增 `wake` 模块及模块内测试；在 `main.rs` 接入状态、路由、持久化初始化及账号删除。
- Flutter：新增开机模型、服务、Provider 和页面；在 `app.dart`、设备页/设置页接入，在账号生命周期中处理助手停用。
- Android：新增 `WakeRelayService`、WOL 编码/网络发送及凭据存储；更新 `MainActivity.kt` 和 Manifest。
- Windows：读取网卡配置并注册开机目标、在应用运行期间报告上线；不实现桌面采集或输入控制。
- 文档与公开说明：说明硬件条件、安卓助手及 Windows 远控能力边界，实际发布时同步公开页面。

## 验收

自动验证：

- Rust 覆盖跨账号访问拒绝、凭据撤销、请求过期/重复、任务归属、配置变更、持久化和账号删除。
- WOL 编码验证 102 字节结构、MAC 校验及实际 UDP 报文；断网/停用取消不能继续发包。
- Flutter 覆盖离线配置保留、助手离线、连续点击、等待与未确认状态；不得把发送成功显示成电脑已开机。
- 执行 `cargo check --workspace`、`cargo test -p rdesk_server`、`flutter analyze`、相关 Flutter 新测试及账号恢复/审核真实性回归。
- 打包 Android，并验证桌面/手机入口。实机联调所需设备未连接时明确记录未覆盖。

真实环境验证：

1. 家中安卓连接普通家庭 Wi-Fi，Windows 优先用网线连接同一 LAN，先验证 LAN 实际唤醒能力。
2. 控制端关闭 Wi-Fi 使用蜂窝网络，或使用另一网络的电脑发起请求。
3. 分别测试睡眠、休眠及完整关机；不以其中一种成功代替另外两种。
4. 安卓锁屏并放置至少 30 分钟后再次尝试；验证断网恢复、助手关闭、退出登录及过期请求不会迟到执行。
5. 电脑关机、安卓助手保持锁屏，分别在隔夜、24 小时及 48 小时后从外网触发，记录整条链路时间和真实开机结果；较长时段验证未做完时明确标记待验证，不提前声称长期稳定。
6. 核实电脑确实启动与应用确实上线两类结果，并记录具体 Windows 网卡/电源状态及安卓型号。若隔夜失败，先保留各阶段记录，不先重启全部设备而丢失现场。

服务端部署是独立动作：本地实现与测试完成后提供变更和验证结果，再进行部署确认。只有真实外网开机链路验证通过，才报告远程开机已验证。
