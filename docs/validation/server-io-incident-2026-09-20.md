# 2026-09-20 服务器 I/O 拥塞调查与优化建议

## 结论与边界

直接故障已确认是持续磁盘读 I/O 饱和，造成系统级 I/O 等待和大量进程阻塞；不是容量耗尽，也未查到本次 OOM 杀进程记录。最可能的触发因素是本轮在内存余量很低的生产机上执行 Rust 构建，引起内存回收和文件页反复读入。没有故障期间的逐进程 I/O 历史，不能证明所有读盘量均来自 rustc，也不能声称重启修复了根因。

生产实例为 ecs.e-c1m1.large，2 vCPU / 2 GiB。操作系统可见内存 1891 MiB，运行 8 个 Docker 容器（包括 MySQL 和多个 Node/Next 服务）及 RDesk。服务器端构建使用 CARGO_BUILD_JOBS=1，但没有内存或读写限额；这种执行方式不足以保护生产。

## 容量与配置发现

- 根分区 40 GiB，已用 32 GiB，可用 5.9 GiB，使用率 85%；inode 使用率 19%。容量需要保留余量，但不是此次告警的含义。
- Docker 镜像约 6.5 GB，其中约 3.1 GB 被报告为可回收。该数值不是删除授权；先核对回滚保留需求，再定向清理。业务卷不在清理建议中。
- MySQL 当前约 417 MiB，qingsong-notes 约 190 MiB，siteharbor 约 102 MiB，其他服务和系统还需额外内存。
- 初次取证时，`/etc/sysctl.d/99-siteharbor-lowmem.conf` 设置 swappiness=10，但 `/etc/sysctl.d/99-sysctl.conf` 链接到 `/etc/sysctl.conf`，后者值为 0，实际运行值为 0。后续已修复，见下方执行记录。
- 目前容器未设置独立内存限额。限额应按业务峰值评估后设置，避免直接套用小限额导致服务被杀。
- 已有 2 GiB swap；dnf-makecache.timer 为 disabled，无需重复增加 swap 或再次关闭该定时器。

## 优化顺序

1. **先分离构建与运行**：按用户的全局要求，在本地生成与 Anolis 8 兼容的成品；必要时补齐本地交叉编译、容器或虚拟机环境。服务器只做接收、替换、校验与必要的服务重启，不承担编译或打包。不要在这台生产机进行压力复现。已更新部署说明和本地 Agent 指引。
2. **按现有内存优化**：用户已说明当前无法增加内存，近期按现有 2 GiB 规格执行，不购买或升级配置。先移除构建负载、观测各服务峰值；本次 CPU 计算不是瓶颈。
3. **统一 swap 策略**：已消除 0 与 10 的覆盖冲突，并使原定的 10 生效。它不是根治，也不能替代构建隔离和内存容量。不要 swapoff，也不要把 swap 无限增大。
4. **限额和观测**：按实际峰值为服务制定内存预算；构建环境独立限 CPU / 内存 / I/O。将主机采样缩短至约 1 分钟，关注 MemAvailable、iowait、await、实例带宽和 IOPS。建议起始告警：MemAvailable 持续低于 300 MiB、iowait 持续超过 20%、文件系统使用率超过 85%，再根据基线调整。
5. **容量整理为次要工作**：审查未使用镜像、历史构建目录和日志保留，目标保留至少约 20% 空间。不要执行无差别 docker prune 或删除业务卷。

初次调查完成了取证、恢复状态验证、官网故障提示撤除和部署说明更新。后续优化如下；没有购买扩容、清理业务数据、改数据库参数或重新在生产构建。远程开机配套服务仍未部署。

## 13:41–13:42 后续优化执行与验证

用户要求全局遵循本地构建后上传，并明确当前不能增加内存。已将规则写入全局 Agent 指引及用户授权的记忆扩展记录，读回确认；项目部署流程同步移除服务器编译步骤。
